# A4 — Supply-chain attacker

**Capability summary:** an attacker who compromises a build-time
input — a transitive crate, a third-party GitHub Action, a release
tarball mid-flight, the install bootstrap script, or the helper
binary (`gitstatusd`) the prompt depends on. They cannot
compromise the maintainer's local machine, the GitHub Actions
OIDC issuer, Fulcio, or Rekor (out of scope per `SECURITY.md`).
Their goal: ship malicious code to a user's machine via a path
that looks legitimate.

## Threats

### T-A4.1 — Compromised crate in the dependency tree
- **State:** **done.** `deny.toml` runs `cargo deny check` with:
  - `[advisories]` `yanked = "deny"`, no ignores
  - `[licenses]` strict allow-list (MIT / Apache-2.0 / BSD /
    ISC / Unicode-3.0 / Unicode-DFS-2016 / CC0-1.0 / Zlib /
    MPL-2.0 / 0BSD); `confidence-threshold = 0.9`
  - `[bans]` `multiple-versions = "warn"`, `wildcards = "deny"`,
    explicit deny list (lazy_static / chrono / tokio / async-std)
  - `[sources]` restricted to crates.io
- **Cite:** `deny.toml` (file is 65+ lines; head shown in audit
  preparation).

### T-A4.2 — Retagged third-party GitHub Action
- **State:** **done.** Every third-party `uses:` in
  `.github/workflows/release.yml` is pinned to a commit SHA with
  a `# vX.Y.Z` comment. `actions/checkout@de0fac2e…`,
  `sigstore/cosign-installer@398d4b0e…`,
  `actions/attest-build-provenance@e8998f94…` — verified at
  lines 81, 210, 237 respectively.
- **Cite:** `.github/workflows/release.yml:81` (checkout),
  `.github/workflows/release.yml:210` (cosign-installer),
  `.github/workflows/release.yml:237` (attest-build-provenance).

### T-A4.3 — Unsigned release tarball / no provenance
- **State:** **done.** Release tarballs are signed with cosign
  keyless `sign-blob`, producing a `.cosign.bundle` sidecar.
  SLSA build-provenance attestations are generated by
  `actions/attest-build-provenance`. Both are uploaded as
  release assets.
- **Cite:** `.github/workflows/release.yml:208-225`
  (`sigstore/cosign-installer@v3.9.2`, `cosign sign-blob`),
  `.github/workflows/release.yml:237` (`attest-build-provenance@v2.4.0`),
  `.github/workflows/release.yml:280` (`.cosign.bundle` asset
  upload).

### T-A4.4 — Compromised `gitstatusd` upstream tarball
- **State:** **done.** `install.sh` defaults to the `pinned`
  helper-acquisition mode and refuses to install unless the
  binary sha256 matches the value at
  `crates/p10k-rs-git/data/gitstatusd-pins.toml`. The
  `p10k-rs verify` subcommand re-runs the same check on demand
  with stable exit codes. The weekly `pin-gitstatusd.yml`
  workflow probes upstream for new releases and opens a PR;
  maintainer review lands the bump.
- **Cite:** `SECURITY.md:84-157` (full lifecycle documented),
  `.github/workflows/pin-gitstatusd.yml` (file present).

### T-A4.5 — `get.sh | bash` clones `main` instead of a release tag

- **Cite:** `get.sh` (script present at repo root; line-level

## Residual gaps (ranked, this attacker class)

1. **`get.sh` bootstrap behaviour not re-walked this audit.**
   THREAT-MODEL.md flagged "clones `main`, not a release tag"
   as P0.8. The script is present; deep walk deferred to next
   audit cycle. **Action item.**
2. **crates.io publish still TODO** (release-checklist
   commitment). Once published, `cargo install` is a new
   distribution channel whose attacker-influenceable inputs
   (crates.io itself) are out of scope per SECURITY.md, but
   downstream packaging (homebrew, AUR, nixpkgs) should
   mirror the sha256-pin discipline; documentation exists
   for the `gitstatusd` pin but not yet for the `p10k-rs`
   binary itself.
3. **Per-asset sha256 sidecar on Windows install path** is
   noted in project memory `project_windows_port_2026_05_26.md`
   as a known TODO blocked on a Windows host; not closed by
   this audit.
4. **No reproducible-build attestation** beyond what the
   default Cargo / GitHub-Actions environment provides.
   `SOURCE_DATE_EPOCH` / hermetic rebuilds are tracked in
   THREAT-MODEL.md as a P1.2 item; not landed.

## Conclusion

The supply chain has gone from "weakest link" (per the original
THREAT-MODEL.md verdict) to among the strongest. cosign
keyless + SLSA build-provenance + SHA-pinned Actions +
`cargo-deny` + `cargo-semver-checks` + `insta` schema freeze +
weekly `gitstatusd` pin-rotation PR + `p10k-rs verify` —
the only meaningful residuals are the `get.sh` re-walk action
item, the as-yet-unpublished crates.io presence, and the
Windows sha256 sidecar. None of these are exploitable as
"compromised tarball reaches a user undetected" today; they
are gaps in coverage discipline rather than missing primitives.
