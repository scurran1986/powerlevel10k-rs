### Why ratios, not absolutes

WSL2 inflates all absolute numbers. On native Linux, gitstatusd reportedly hits
~25 ms on the kernel; here we measure 83.8 ms. That's a 3.4× WSL2 tax. Apply
the same tax to gix-only and we'd expect ~400 ms native, vs the 80 ms
allowable. **Ratio (16×) is the load-bearing signal.**

## What we now know with high confidence

1. **Subprocess gitstatusd is dead.** 1005 ms (ripgrep) and 1196 ms (kernel) for fork/exec is an order of magnitude over the user-facing budget on its own. Production must integrate via long-lived daemon, in-process FFI, or pure-Rust port.
2. **Hybrid is worse than gix-only on every fixture tested.** 2.2× slower on ripgrep, 2.1× slower on kernel. The untracked-cache + parent-fd-walker bet does not pay off in this implementation. Possible explanations:
   - `openat`/`fstatat` per file is more syscalls than `read_dir`'s batched `getdents`. The walker would need batched `getdents` itself (which `RawDir` provides) AND aggressive parallelism (rayon) to compete with `gitstatusd`'s multi-threaded scan.
   - The cache miss path does extra work (binary serialization, atomic write) that is unamortized when most directories are cache-cold.
   - Single-threaded by spike design. `gitstatusd` is multi-threaded; gix-status uses some parallelism internally. Hybrid is the lone single-threaded contestant.
3. **gix-status is ~16× slower than gitstatusd on real-sized repos.** This is an indictment of either (a) gix's `index_as_worktree` algorithm, (b) gix's choice of safe `read_dir` over batched `getdents64`, or (c) some combination. It is not a problem the spike's hybrid impl solves.
4. **`gitstatusd`'s 0.5 ms internal timer vs 1.28 ms wall** on ripgrep tells us ~0.8 ms of the wall measurement is IPC overhead in `run_baseline.sh`'s coproc loop. This is acceptable — the production path will use the same wire protocol.

## What we still don't know

- **Where does gix's time actually go on the kernel?** A `gix-status` flame graph would tell us whether the win is in the walker, the diff, the index parse, or somewhere unexpected. Pure pivot-or-not doesn't need this; if we're picking a non-gix architecture, the answer doesn't change anything.
- **Would aggressive parallelism (rayon over the index-dir-tree, like gitstatusd's `IndexShard` design) close the gap?** Plausibly the gap shrinks to 4-8×. Probably not enough.
- **Chromium numbers** — we don't have them. The kernel data is sufficient to fire the PIVOT trigger; chromium is not necessary for the call.

## Pivot directions (Sean's pick)

1. **`gitstatusd-rs` shim** — keep using `gitstatusd` (the prebuilt binary, long-lived), but implement a Rust-side IPC layer + state machine. The Rust side owns segments, config, instant prompt, wizard — everything except the git subsystem. Lowest risk; the prompt experience is decoupled from gitstatusd's velocity (which is "frozen" per upstream README).
2. **C++ FFI to libgitstatus** — link the C++ core as a library. Higher risk (linking dynamic libgit2, build complexity, MSRV implications), but faster than (1) by avoiding IPC. Unclear if `gitstatusd` exposes a C-callable API; would likely need a small wrapper.
3. **Pure-Rust port of `gitstatusd`'s algorithm** — multi-threaded `IndexShard` walker, custom `getdents64` batching, mtime untracked-cache with the `check_dir_mtime` viability probe, no gix dependency for the hot path. Highest cost; explicitly "frozen" per p10k upstream because it's a decade of engineering. **TARS rates this as "do not."**

## Recommended next step

Pick option **1**: `gitstatusd-rs` shim. The architectural finding (long-lived daemon required) was already locked in; option 1 simply makes that finding the architecture. The Rust port can be the post-v1 north star if `gitstatusd` ever fails us. p10k-rs ships in 2-3 months on option 1, vs 9-12 months on option 3.

This means the existing `p10k-rs-git` crate becomes a `gitstatusd` client (wire protocol, response parsing, state machine), not an in-process scanner. The `spike-gitstatus` crate is the throwaway deliverable; it has discharged its purpose and can be removed from the workspace once the ADR lands.
