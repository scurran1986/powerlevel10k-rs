## Decision-blocking gap

**`MVP-SPEC.md` § 0 thresholds are for chromium and linux kernel, not ripgrep.** ripgrep was always the harness-validation fixture, and it is not in the threshold table:

```
| Scenario          | gitstatusd target | gix-only allowable | hybrid target |
|-------------------|------------------:|-------------------:|--------------:|
| Chromium hot      |          30.9 ms  |          ≤ 100 ms  |      ≤ 60 ms  |
| Chromium cold     |         291 ms    |          ≤ 600 ms  |      ≤ 400 ms |
| Linux kernel hot  |          ~25 ms   |          ≤ 80 ms   |      ≤ 50 ms  |
```

ripgrep is ~10× smaller than the kernel and ~50× smaller than chromium. Our ripgrep numbers indicate:

1. **gitstatusd has roughly 25-50× headroom on small repos** (1.3 ms vs its 25-30 ms target on big ones). The ratio gix-only:gitstatusd will narrow as repos grow because gitstatusd's per-call overhead amortizes.
2. **Hybrid is _slower_ than gix-only on ripgrep**, which contradicts the spike's hypothesis. Likely culprits: per-file `openat`+`fstatat` overhead dominates on small worktrees; the untracked-cache file write/read cost is unamortized; the cache-miss path does extra work that pays off only at scale.
3. **Subprocess gitstatusd at 1005 ms confirms a load-bearing architectural finding**: `p10k-rs-git` must integrate via long-lived daemon or in-process — never fork/exec per prompt.

**We do not have data sufficient for GO / HYBRID / PIVOT.** We have data sufficient for "this is a real risk; need chromium or kernel numbers."

## What we *can* commit to before chromium/kernel data

- **Architectural decision (locked)**: any gitstatusd integration, if we keep one as a fallback or comparison, must be long-lived. This rules out the "subprocess gitstatusd per prompt" naive design.
- **Hybrid is provisionally suspect**: needs to demonstrate non-trivial speedup over gix-only on at least the kernel before it earns its complexity.
- **gix-only is the simpler architecture and is cheap enough on ripgrep to be inside the user-facing budget** (6.6 ms is 1.5% of p10k's 100 ms instant-prompt target). Whether it stays inside on chromium is the open question.
